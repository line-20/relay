# Review: PR #34 — wire the resume checkpoint into /handover

**RESOLVED — verdict now approve.** The original review found 3 blockers (below), all in the
first commit's mechanism. Fixed in commit `43b3882` (temp-index replication + Write-tool JSON +
recursive provider scan) and re-reviewed: backend and security **approve**, architecture **no

Original findings, all now ✅:

**Original verdict: request-changes (3 blockers).** All three 🔴 were confirmed by tracing the code, not
just taken from the specialists. Two of them (🔴-2 architecture, 🔴-3 backend) share one root
cause: `_replicate_checkpoint` makes a **real working-tree commit on the shared main checkout**
instead of using the temp-index-from-`FETCH_HEAD` pattern that every other `main`-writing surface
in Relay uses. That single mechanism is both unsafe under concurrency and functionally broken in the
real 4a-then-4b topology. The security 🔴 is independent.

## 🔴 Blockers

### 🔴-1 · Command injection via the Step 4a checkpoint JSON heredoc
`plugins/relay/commands/handover.md` (Step 4a `cat > "$RESULT" <<JSON`), mirrored in `rlh.md`.
The heredoc delimiter is **unquoted** (`<<JSON`, not `<<'JSON'`), and the agent fills
`next_slice`/`scope_edges`/`open_questions`/`stage`/`$SLUG` from free-text handover content. An
unquoted heredoc performs `$(...)`/backtick command substitution on that content before the file is
written — so handover prose that quotes an external PR body, an issue, a filename, or a shell
snippet can execute arbitrary commands in the **main checkout**, immediately before an automatic
`git push` to `origin/main`. **Fix:** build the JSON with `jq -n --arg` (or `python3`) passing every
dynamic value as data; never interpolate session content through the shell. (security-specialist)

### 🔴-2 · Step 4a violates the parallel-worktree-safe-commit invariant
`plugins/relay/commands/handover.md` Step 4a + `scripts/relay_harvest.py` `_replicate_checkpoint`
(`git add`/`git commit --only` in `$MAIN`'s real working tree + index, ~line 770-780).
`docs/conventions.md` ("Parallel-worktree-safe commits") requires every write to `main` to go via
the temp-index primitive (`read-tree FETCH_HEAD → write-tree → commit-tree`) precisely because ~10
sessions run concurrent worktrees against one main. Step 4a instead points `--repo "$MAIN"` at the
shared checkout and does a literal working-tree commit that moves `$MAIN`'s local HEAD and contends
on its `index.lock` — on the mainline path, every handover. The code comment even names
"an index.lock race in the shared checkout" as an anticipated failure. **Fix:** give
`_replicate_checkpoint` a temp-index mode (commit the checkpoint blobs against `FETCH_HEAD`, never
touch the working tree), matching Step 4b and `/tidy`. (solution-architect)

### 🔴-3 · Checkpoint push is a permanent non-fast-forward after the first handover
`scripts/relay_harvest.py` `_replicate_checkpoint` (`git push origin main` at ~line 780) +
`handover.md` 4b (`git push origin "$COMMIT:main"`). 4b (and Step 4.5 tidy) advance **origin/main**
by pushing a commit built in the slice worktree straight to the ref — they never advance the main
checkout's **local** `main`. So: handover-1 4a pushes cp1 (in sync) → 4b pushes hv1 to origin/main
while `$MAIN` local main stays at `base+cp1` → handover-2 4a commits cp2 on that stale local main,
and `git push origin main` is rejected non-fast-forward, permanently. Every checkpoint after the
first reports `committed:true, replicated:false`, and the reconcile branch (~line 761-766) returns
without re-pushing a locally-*committed* checkpoint, so it never self-heals. Cross-device resume —
the entire point of the slice — silently stops working after one handover. The suite passes only
because no test advances origin/main independently of `$MAIN` local main. **Fix:** same as 🔴-2 —
build the commit from `FETCH_HEAD` via a temp index so 4a never depends on `$MAIN`'s local main
being current; on non-ff, re-fetch-ff-retry. (backend-developer)

## 🟡 Should-fix

- **Provider-neutrality denylist is shallow.** `scripts/relay_harvest.py` `validate_result`
  (166-175) / `_validate_resume_delta` only scan top-level keys for `session_id`/`claude_session`/
  `provider`, but `_build_checkpoint` copies `references`/`resume_delta` **wholesale** into the pushed
  checkpoint. A nested or oddly-named secret lands durably in shared git history. Recurse the scan and
  bound `_build_checkpoint` to an allowlist. (security)
- **Checkpoint written to `$MAIN`'s tree before the branch-guard check.** `apply_one` `_atomic_write`s
  the checkpoint/marker into `$MAIN` before `_replicate_checkpoint` verifies `$MAIN` is on the durable
  branch; when it isn't, the write is left as stray residue, contradicting the "non-fatal, nothing
  disturbed" framing. (architecture) — resolved for free by the 🔴-2 temp-index fix.
- **CLI `main()` flag mapping untested.** `scripts/relay_harvest.py` (822-829): all four new tests
  call `apply_pending` directly; nothing exercises `rh.main([... "apply", "--no-projection",
  "--no-board"])`, so a flipped flag condition ships undetected. Add one `main()`-level test. (test)
- **Flag independence not pinned.** No test exercises `write_projection=False` with
  `board_path=self.board` (the two flags are independent in code, always paired at the call site).
  Add a case or a comment noting the pairing is intentional. (test)
- **New flags never combined with a replication-failure path** (offline / off-durable-branch). Add
  one variant to lock the orthogonality. (test)
