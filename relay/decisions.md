- **2026-10-13 · state/notes-branch slice 2 · writers, `state init|export|status`, and the commands** — one writer, `relay_harvest.py state-commit` (temp index onto the fetched tip, one attempt, `--add/--remove/--move`), replaces the hand-rolled `read-tree … commit-tree … push origin $COMMIT:main` in `/handover` 4b + 4.5, `/tidy`, `/explore`, `/refine`, `/next`, `/watch`, `/persist` (the marker); the checkpoint push (`_replicate_checkpoint`) targets the notes branch via `_state_target`. Why one attempt and no retry inside: a retry that replays a stale `board.md` would clobber a sibling's row; callers re-read and re-apply (`/tidy` already loops that way). Why `--move` takes content from the branch tip: archiving must not need a working-tree copy of notes that live only on another ref. Writers never create the branch (challenger condition 3); `state init` is the only creator, seeded as an orphan from `main`'s volatile notes, no force-push so a racing init loses cleanly; `state export` is the way back (it OVERLAYS the notes onto `main`; `--prune` deletes main-only notes, `--delete-branch` resets the branch so a later re-enable seeds fresh). The review pass added: `state tip` / `show --at` / `--base` so a shared note (the board) is built on the exact tip it was read from and a sibling's edit is rejected, not overwritten (the old hand-written snippet had this property and it must not be lost); `--put` and `--sync-dir` so `/tidy` and `/handover` edit a snapshot (which records its own tip) instead of the working tree; NUL-separated index records and control-character refusal (a newline in a name could inject entries); literal pathspecs; notes-only in both modes; a mass-delete guard on sync; the safe switch-on order is land the setting, then `state init` immediately. The allow-list gained `archive/` and `audits/` (written by `/next` next to the board). `/persist` is ordered: durable docs on `main` first, the Distilled marker (a note) only after they landed, so `/tidy` can never prune a brief whose knowledge is not on `main`. **Known limit:** review reports from `/review` are committed on the feature branch and therefore reach `main`, not the notes branch. **Reverses if:** one attempt per call proves too chatty for `/tidy` (then add a bounded replay that re-reads the board itself).
- **2026-10-13 · state/notes-branch slice 1 · where Relay's coordination notes live, and who reads them** — chose **A: an opt-in `state.branch` (orphan branch, e.g. `relay-notes`) holding only the volatile notes (`board.md`, `briefs/`, `handover/`, `reviews/`, `harvest/`), read through ONE ref-aware reader**; unset = today's behaviour, byte for byte. Why: castles-erp adopted a merge queue and every `/handover` push to `main` moved `main` under a queued batch (a rebuild plus a ~10 min CI run). The challenger (autonomy: challenge) ruled A over a `refs/relay/state` ref (C): once readers go through `git show`, A vs C is close, and A wins on browsability in the GitHub web/mobile UI, ruleset protection against force-push/deletion, and the default fetch refspec; GitHub also refuses a PR between unrelated histories, so an orphan cannot be merged into code by accident. **This is the decision slice 3 (2026-09-17, below) named as its own reversal condition:** resume now reads checkpoints/board/briefs via `git show` from an arbitrary ref (`state_snapshot`, `read_note`, `list_notes`, `_resolve_ref(state=…)`), not off the checked-out working tree. Four conditions from the ruling, all enforced here or in the slices after it: (1) every reader reads the ref, never the worktree, when the setting is on (a worktree forked from main holds a frozen copy that would resume the wrong lap); (2) the setting is read from the REMOTE durable branch's `relay.config.json`, so a slice branch forked before the switch still follows it; (3) writers never create the branch (only an explicit init does), and a missing branch fails loud, never falls back to the durable branch; (4) `/persist` splits into ordered writes (durable docs first, the Distilled marker only after they land). The slice-1 review (backend + test) added: a set-but-unusable setting raises instead of reading as unset; the remote config wins and the checkout's file is used only when there is no remote durable branch to read; every git call runs from the top-level (`ls-tree -z`), so subdirectories and non-ASCII names work; `ls <root>` merges notes from the branch with the rest from main; an absolute note path still resolves against the branch.
- **2026-09-17 · contracts/handover-contract slice 4 · which command owns the checkpoint write, and how it commits** — chose **A: `/handover` (Step 4a) owns both emit and apply**, keeping the commit/push logic in the tested `_replicate_checkpoint` (not a reimplementation in handover.md bash the Python suite can't reach — the challenger's objection to "Option B"). `/handover` owns emit **and** apply because Step 1/3 already gather the exact resume state `emit` needs, and implicit apply is what makes "resume just works" true with no remembered worker step. **The slice-4 review (PR #34, `relay/reviews/pr-34-2026-09-17.md`) then reversed the commit *mechanism*** — three blockers converged on it: the original `_replicate_checkpoint` did a real **working-tree commit in the shared main checkout**, which (a) violated `docs/conventions.md`'s parallel-worktree-safe-commit invariant [arch 🔴], and (b) was functionally broken — Step 4b advances `origin/main` without advancing any local `main`, so the *second* handover's checkpoint sat on a stale local main and its push was a **permanent non-fast-forward** [backend 🔴]. Resolution: `_replicate_checkpoint` now builds the commit with the **temp-index-onto-freshly-fetched-tip** primitive (the very thing "Option B" pointed at, but kept in tested Python) — no working-tree/index/HEAD mutation, no branch guard, runs from **any checkout including the slice worktree**, so `/handover` no longer reaches into the main checkout at all. A non-ff from a sibling advancing the remote mid-lap self-heals on the next fetch-and-retry. This is the challenger's A-vs-B synthesis: B's mechanism, A's tested home. Refinements retained: (1) checkpoint-first ordering, non-blocking (resume falls back to the Markdown handover, no fail-closed); (2) **`--no-projection`** so `/handover`'s richer handover stays canonical; (3) **`--no-board`** so Step 4b owns the board commit; (4) WAL (`relay/harvest/*/results/`) gitignored. Also from the review: the security 🔴 — the Step 4a result JSON is written with the **Write tool, never shell-interpolated** (an unquoted heredoc let handover prose command-substitute before an auto-push); and the provider-neutrality scan is now **recursive** (a nested `session_id` would otherwise reach the pushed checkpoint). **Reverses if:** a future need forces the checkpoint onto a ref the temp-index-onto-durable-tip can't reach (e.g. per-worktree checkpoints), which would reopen the ref question of slice 3. Proven by the rebuilt `CheckpointDurabilityTest` (the consecutive-handover non-ff regression, any-branch replication, foreign-staged-file isolation, nested-provider rejection, CLI `main()` flags).
- **2026-09-17 · contracts/handover-contract slice 3 · which git ref the checkpoint commits+pushes to** — chose **A: commit `relay/harvest/<slug>/checkpoint.json` to main and push it, per-checkpoint (opportunistic, non-blocking — the same R1.6 discipline as `autosave`), NOT throttled to the session boundary** (autonomy: challenge). Decisive fact the brief under-weighted: `discover_active`/`resume_context` read checkpoints by walking the **checked-out working tree** (`relay/harvest/*/checkpoint.json`), not via git refs — so a fresh-device clone (which checks out `main`) only finds all active items if every checkpoint lives in main's working tree. That kills **B** (topic branch — scattered across branches the main checkout can't see, deleted on merge) and **C** (`refs/relay/checkpoints/*` — fetched by no default clone and in no working tree, so the readers couldn't see it without a rewrite). Matches R1.10 (board/handover/brief already live on main for this device-independence reason). Throttle rejected: once origin is the location that matters (cross-device), a once-per-session push leaves origin stale mid-session — reintroducing the exact loss window the feature closes; R1.5 wants "a recent durable checkpoint must always exist." A `replicated` flag records whether the push landed. **Reverses if:** a fresh-device resume is redesigned to read checkpoints via `git show`/`cat-file` from arbitrary refs (then C reopens, churn-free), OR the checkpoint is written per-worktree rather than into the shared main checkout (then B becomes natural). Both are one grep to check. Open sub-decision escalated to maintainer: per-lap checkpoint commits churn main's history — a product/workflow consequence, the maintainer's call.
